### 핵심 발견

**전체 TPS가 동시 요청 수와 무관하게 ~66 TPS에서 수렴한다.**

```
동시 1 → 51.9 TPS  (GPU가 아직 포화되지 않은 상태)
동시 2 →  65.7 TPS  ← GPU 포화점 도달, 이후 일정
동시 4 →  65.6 TPS
동시 8 →  66.3 TPS
```

vllm의 **continuous batching** 덕분에 여러 요청을 하나의 배치로 묶어 처리한다.
GPU가 이미 99% 포화 상태이므로 요청이 늘어도 전체 처리량은 늘지 않고,
개별 latency만 요청 수에 비례해 증가한다.

### 결론

| 항목 | 값 |
|---|---|
| GPU 포화 동시 요청 수 | **2개** |
| 최대 전체 처리량 | **~66 TPS** |
| 실용적 동시 요청 상한 | **2~3개** (latency 20s 이내) |
| 8개 동시 시 개별 대기 | 평균 43.5s — MCP timeout 주의 |

→ MCP 클라이언트(Claude Desktop 등)에서 동시에 여러 tool call이 발생할 경우
  **2개까지는 latency 영향이 제한적**, 그 이상은 큐잉 지연 급증.

## 주요 발견

### 1. Thinking 모드 (chain-of-thought)
모든 응답이 `<|channel>thought ... <channel|>` 구조로 감싸임.  
내부 사고 과정이 먼저 생성된 뒤 `<channel|>` 이후 실제 답변이 출력됨.

```
<|channel>thought
* 문제 분석
* 여러 접근 방법 검토
* 최종 선택<channel|>
[실제 답변]
```

→ max_tokens이 부족하면 사고 과정에서 토큰을 다 소비해 답변이 잘림 (이전 테스트 실패 원인)  
→ **32768로 설정 시 모든 테스트 완전한 답변 생성**

### 2. CPU 패턴

```
유휴: 0~0.2%
추론 시작(~3초 후): 급격히 55~70%대로 상승
추론 중: 60~76% 지속
추론 완료: 0~1%로 즉시 복귀
```

- CPU 사용률이 **60~76%** 로 높은 편 — Apple Silicon NPU(Neural Engine)가 아닌 CPU 위주 연산
- 단일 요청 처리 중 다른 작업 여유 없음

### 3. 메모리 패턴

```
유휴: RSS 1022 MB (4.2%)
추론 중: RSS 1022~1023 MB (변화 거의 없음)
```

- 모델 가중치가 이미 메모리에 로드된 상태 유지
- 추론 중 추가 메모리 할당 거의 없음 (< 1 MB 증가)
- **메모리는 안정적** — 장시간 운영해도 메모리 누수 없을 것으로 예상
